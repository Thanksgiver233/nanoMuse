# nanoMuse 1.0.10 · Triage

🐉 **nanoMuse `1.0.10` “Triage”** The runtime learns to judge how hard a run looks before it starts, and to send the hard ones to a stronger model.

This is the fork's release after its v1.0.9. It collects seven pull requests (#19 to #25) built by studying OpenMausBot's design and re-implementing the parts that fit this codebase: a decision layer, a squad with a real task ledger, a tool bridge, and grants bound to the policy they were given under. The full test suite went from 1415 to 1545. Every new behaviour sits behind a switch that defaults off or to watching only, so an upgrade changes nothing until the switch is set.

## Highlights

- **A decision layer that first watched, then learned to act.** With `[decider]` on, a run first asks a model to score the task's difficulty as a probability distribution over five graded levels. The answer is validated before it is believed (a closed option set, probabilities summing to 1, the chosen answer the most probable one), the call is recorded in the cost ledger, and one line lands in the decision log: the score, the probabilities, the latency, and a hash of the message, never the message itself. In shadow mode, still the default, that is all it does. In active mode, with an `escalated_model` named, the levels at or above the threshold count as escalated and their probability mass gates the switch: a run over the line runs on a client built for the escalated model, for that run only, and the original client is restored when the run ends, on the exception path too, after the run's cost entry has been written under the model that actually ran. Calibration is reported as it came out: on the new synthetic benchmark corpus in `scripts/` (30 hand-labelled messages), the two cheapest judging models returned no answer that passed validation (0 of 60 and 0 of 30), so with either of them the layer fails open and never acts; with a judge that keeps the answer format (deepseek-ai/DeepSeek-V4-Flash, 27 of 30 valid), the rule at the 0.6 default acted only on items labelled hard: precision 1.0, no false trigger below level 4, 11 of 12 hard items caught. The benchmark is synthetic, not real usage; the configuration docs say to re-check the threshold against shadow logs once a deployment has them. The layer never approves or refuses anything; that stays with the Sentinel.
- **Squad assignments became real.** A dispatch is written to a persistent task ledger (`squad.db`) with a seven-state lifecycle whose terminal state is written once, guards at enqueue time, and a reconciliation pass at startup that reads the cost ledger as evidence (#20). Role presets run the assignments: research and verify with a role prompt, a read-only tool face judged per call and the cheap model tier, execute with the full face on the default tier; a dispatch that names no mode is a consult and runs read-only (#21). Each assignment is frozen at enqueue with a risk ceiling, the tighter of its parent's level and its preset's cap, and a call assessed above the ceiling is refused in front of the Sentinel, before the Sentinel is consulted (#22). A live acceptance run dispatched a real research subtask: it settled as completed, its result matched the file it was sent to read, and its cost entry matched the vendor's usage figures item for item.
- **A tool bridge for small context windows.** With `[tool_bridge]` on, the tool list sent on every call keeps a direct core of seven tools plus two meta tools, and the rest are reached by name: find_tools searches names, purposes and keywords, use_tool runs the named tool through the same Sentinel guard, audit log and cost ledger as a direct call. Sending tools and the approval machinery's names never go through the bridge. The bridge buys context headroom, not savings: a bridged call costs what the direct call costs, and it passes the guard twice, once for the envelope and once for the named call (#23).
- **Standing permissions follow the policy they were given under.** A grant is stamped with a fingerprint, a hash of the `[sentinel]` policy fields (the mode, the always-ask, always-allow and deny lists, the egress allowlist, the rules, the taint switch). While the policy fingerprints the same, the grant settles calls as before; a change pauses the grants given under it, changing it back revives them, and the skip is logged. Reordering a list is not a change; reordering the rules is. The gatekeeper stamps and checks grants in its own store from its own copy of the same settings, so the wire protocol is unchanged (#24).

## Upgrade Notes

- Standing grants written before this version carry no fingerprint and are not honoured; give a standing permission once more after upgrading.
- `[decider] mode` accepts `active` as well as `shadow`, and `escalated_model` is new. Both default to the old behaviour.
- Android versionCode 53. The relay is unchanged and keeps its own version.

**nanoMuse `1.0.10`“Triage”**：运行时先判断一轮任务的难度，再决定要不要把难的送去更强的模型。

这是本 fork 在 v1.0.9 之后的版本，收了七个 PR（#19 到 #25），做法是研读 OpenMausBot 的设计，把适合这个代码库的部分重新实现：决策层、带真实任务账的小队、工具桥，以及与策略指纹绑定的 grant。全量测试从 1415 涨到 1545。所有新行为都挂在默认关或默认只观察的开关后面，不打开就不改变现有行为。

- **决策层：先只看，再真动手。** 开 `[decider]` 后，一轮开始前先请模型按五档给出难度概率分布，答案先过校验（选项封闭、概率和为 1、所选即最高概率）才采信，调用进成本账本，决策日志只记分数、概率、延迟和消息的 hash，不记原文。shadow 是默认值，只记不做。active 模式下再配 `escalated_model`：阈值及以上档位的概率质量过线，本轮才换成升级模型，跑完恢复，异常路径也恢复，成本按实际跑的模型记。校准如实写：30 条合成基准上，两个最便宜的判定模型一条合格答案都没有（0/60、0/30），用它们这层等于不存在；换 DeepSeek-V4-Flash 判定（27/30 有效）后，0.6 阈值只触发在标为难的条目上，精确率 1.0，低档零误触发，难题 12 条抓住 11 条。这是合成基准，不是真实使用日志，文档里写明攒够 shadow 日志后要复校。这一层从不决定审批，审批仍归 Sentinel。
- **小队任务成真。** 派活写入持久化账本（`squad.db`），七态生命周期、终局只写一次、入队守卫、启动时按成本账本对账（#20）。research、verify、execute 三个角色预设真执行：只读预设过两层判定，没写模式的派活一律 consult 只读（#21）。每个任务入队时冻结风险上限，执行时超限的调用在 Sentinel 之前就被拒，Sentinel 零咨询（#22）。真跑验收派过一次 research 子任务：正常 settle、结果与所读文件原文一致、成本条目与厂商 usage 逐项一致。
- **工具桥。** 开 `[tool_bridge]` 后每轮只发 7 个直列核心工具加 2 个元工具，其余 31 个按名取用，走同一个 Sentinel 拦截点；发送类与审批类工具永不走桥。省的是上下文不是钱，桥调用过 guard 两次（#23）。
- **grant 配置指纹。** grant 打上 `[sentinel]` 七个策略字段的 sha256 指纹；配置一改，旧 grant 暂停生效并记日志，改回去自动复活，不删除；升级前没指纹的旧 grant 不再认，升级后重批一次。Sentinel 与 Gatekeeper 两处同源接线，线协议不用改（#24）。
